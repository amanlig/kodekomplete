From `device-interface`, on a configured Rust/Bluetooth host:

```sh
cargo run --locked -- monitor-victron 'D4:B3:CB:26:5E:75' \
  --key-file /path/to/orion.key \
  --database data/observations.sqlite3

cargo run --locked -- observations data/observations.sqlite3 25
```

For native Windows, from `device-interface` in PowerShell:

```powershell
.\build-windows.ps1
.\target\x86_64-pc-windows-msvc\release\ainavlog-device-interface.exe monitor-victron 'D4:B3:CB:26:5E:75' --key-file "$env:LOCALAPPDATA\aiNavLog\orion.key" --database '.\data\observations.sqlite3'
```

The key paths are examples; create the actual private file first. SQLite defaults
to `data/observations.sqlite3` relative to the process working directory.

## Work remaining beyond hardware validation

- iOS/Android native bridge, permission handling, Keychain/Keystore integration,
  background behavior and platform/device validation.
- NMEA gateway selection and Bluetooth payload reception/framing; CAN fast-packet
  reassembly where needed, AIS assembly where needed, and NMEA observation mapping.
  Existing codecs process complete messages, not arbitrary transport chunks.
- Generic `TransportAdapter`, `ConnectionManager` and `DeviceProtocolAdapter`
  operational integration; these remain stubs. The working Victron monitor uses
  its own advertisement-source interface and supervisor.
- App-wide data storage, retention, access protection and UI integration. Current
  SQLite is an interim local, unencrypted store with no automatic retention/upload.
- Mobile release builds, dependency notices and download-size assessment.
- Wi-Fi remains shelved beyond beta; do not reintroduce it as part of this work.

Victron broadcasts are unauthenticated AES-CTR. Successful decoding and `Good`
measurement quality do not authenticate the sender or prove the entire key is
correct. Real readings must be compared before relying on them. This integration
is read-only and sends no charger control commands.
